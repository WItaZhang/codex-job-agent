# Idea Kickoff：从模糊想法到第一个可用切片

目标：防止"重点模糊、做出来跟想象的不一样"。核心原则是把用户脑子里的判断标准
外化成文档、样例和测试，再写代码。代码是最后一步。

整个流程分 5 个阶段。**每个阶段结束都要停下来，让用户确认后再进入下一阶段。**
不要跳阶段，不要在用户没确认时开始写代码。

## 在本仓库中使用

这是开发流程技能，不是求职运行时技能；不要在处理具体岗位时调用它。下文中的
通用文件名在本仓库对应为：

- `CLAUDE.md` → 仓库根目录的 `AGENTS.md`（长期决策写这里）。
- `spec.md` → 新功能放在 `docs/agent/` 下的独立 spec 文件；确认后的需求同步进
  `docs/agent/IMPLEMENTATION.md`，实际操作约定同步进 `docs/agent/USAGE.md`。
- `tests/fixtures/` → `tests/agent/fixtures/`；生成的合成样例必须标注为
  synthetic，评估用样例遵守 `evals/` 的标注约定。真实个人数据只放在被忽略的
  `data/local`，不要提交。
- 实现仍须遵守 `AGENTS.md` 的模块边界、`configs/` 配置约定和验证命令。

## 阶段 1：采访（不写任何代码）

如果已安装 grill-me skill，优先调用它来完成采访，采访结束后回到本 skill，执行
下面第 6–8 步。没有安装时，按以下方式自己采访：

1. 先用一两句话复述你理解的想法，然后开始提问。
2. **一次只问一个问题。** 等用户回答后再问下一个。
3. 沿着决策树一层层问：先解决上游决定，再问依赖它的下游问题，不要按清单随意跳。
4. 每个设计问题附上你的推荐答案和简短理由，让用户同意或修改，加快速度。能从
   代码库或现有文件里查到答案的，直接去查，不要问用户。
5. 用户回答含糊时要追问（例如"精准"具体指什么？"偏好"从哪里来？什么情况算
   失败？）。优先问清：
   - 使用者是谁，在什么场景用？
   - 输入是什么，输出是什么，做到什么程度算"完成"？
   - 下游有哪些决策依赖它的输出？（不服务于下游决策的东西不做）
   - 哪些部分是确定流程，哪些真的需要模型自主判断？
   - 什么情况算做错了？最不能接受的错误是什么？
   - 第一版明确不做什么？
6. 把结论整理成 `spec.md`：目标、使用场景、输入输出、核心规则、不做的事、未决问题。
7. 把会长期影响实现的关键决策同步写进 `CLAUDE.md`，保证以后的会话都遵守。
8. 请用户审阅 `spec.md`，确认后进入阶段 2。

## 阶段 2：样例（用户掌握"期望结果"）

分工原则：**AI 生成输入，用户判断期望输出。** 这个阶段不要给推荐答案，避免用户
被带着走。

1. 根据 spec 生成 10–20 个输入场景，必须包括：
   - 典型情况
   - 边界和刁钻情况（前后矛盾、信息不完整、一次性的噪音信号、重复信息）
2. **先只给用户看输入，不给期望输出。** 逐个（或分小批）请用户先说出他认为正确
   的结果。
3. 然后再给出你的预期答案进行对比：
   - 一致：记录为样例。
   - 不一致：停下来讨论，弄清谁对、背后是什么规则。把新发现的规则补进 `spec.md`。
4. 鼓励用户加入自己真实数据做的样例，这比生成的更有价值。
5. 把确认后的样例存进 `tests/fixtures/`。

## 阶段 3：最小切片计划

1. 选出最小的一块核心逻辑（通常是整个系统里最关键、最容易出错的那一步）。不做
   UI、不做外部集成、不做次要功能。
2. 写出实现计划：数据结构、模块划分、模型负责什么、代码负责什么（原则：模型负责
   理解，代码负责保证一致性和校验）。
3. 对用户可能不熟悉的设计取舍做简短解释。
4. 等待用户确认计划后再开始实现。

## 阶段 4：测试先行，再实现

1. 先把 `tests/fixtures/` 变成可运行的测试。
2. 再实现，运行测试直到通过。
3. 不要为了通过测试而写针对特定样例的特殊逻辑。
4. 完成后简要告诉用户：实现了什么、测试结果如何、关键逻辑在哪个文件（鼓励用户
   看一眼）。

## 阶段 5：用具体 case 迭代

1. 请用户用真实输入试用。
2. 当用户说"不好""不准"这类模糊反馈时，帮他转化成具体 case：输入是什么、实际
   输出是什么、期望输出是什么。
3. 每个问题先加进测试，再修复，然后跑全部测试，确认没有改坏别的。
4. 这一块稳定后，回到阶段 2 或 3，开始下一块功能，同样流程。

## 全程规则

- 讨论和实现分开：需求想清楚就写进文档。上下文变长或进入新阶段时，建议用户新开
  会话，依靠 `spec.md` 和 `CLAUDE.md` 延续。
- 每次改动保持小而可验证。
- 用户想跳过阶段时，可以简短说明风险，但尊重用户决定。
- 和用户用他使用的语言交流。
