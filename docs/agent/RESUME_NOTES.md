# 面向业务 Agent 开发的项目表达

目标是业务 Agent 应用研发：能够理解业务流程、划分模型与程序职责，处理执行
故障，验证输出质量，并对处理开销作出取舍。这个项目的定位是有完整执行与
验证机制的个人工程项目；技术细节应服务于这条主线。

## 简历版本

**Codex Job Agent｜让 Agent 安全执行不可撤销操作的运行时（以求职投递为案例，个人项目）**

Python · Codex Skills · Pydantic · SQLite · Playwright

- **业务流程与架构：** 面向 Codex 设计并实现求职技能集与本地 Agent 工具运行时，接入
  Greenhouse、Lever、Ashby 三类岗位源，覆盖筛选、材料准备、授权执行与结果追踪；
  将模型的语义判断与 Python 的规则校验、状态管理分离，支持自动处理与人工审核分流。
- **稳定性与故障恢复：** 针对材料变更、并发执行和回执缺失，设计版本绑定审批、
  进程锁及提交意图持久化；结果未知时阻止自动重试，经核实后恢复流程，并将质量
  抽检故障与投递状态隔离，避免辅助流程失败覆盖已确认结果。
- **成本与处理效率：** 设置单次计划规模上限，预留高匹配岗位名额，结合跨来源投递目标
  去重与每日提交尝试限额；默认每十份确认投递抽检一份，以可配置采样控制额外
  模型复核频次，汇总已记录的评审 token 与耗时，支持质量与开销的权衡。
- **质量评测与迭代：** 冻结投递材料，通过独立会话分别审查岗位相关性与事实
  依据，将证据化告警关联根因分析及回归验证；设计内容长短对照、顺序交换和有效
  信息正对照检验评审偏差；项目通过 245 项工程测试和本地 ATS 端到端验证，
  并在六组合成对照上完成十二次独立模型评审。

正文不必额外罗列所有状态名、命令或框架。245 项测试证明工程验证范围，不是
任务成功率；十二次评审是小规模合成案例实验，不是线上质量指标。

## 招聘方应从中读到什么

第一条交代交付对象和职责边界。第二条回答外部工具出错时系统怎样保持正确，
这是执行稳定性。第四条回答模型输出是否可信、如何发现退化，这是内容质量；
两者不能用一个笼统的“可靠性高”替代。

成本条目体现资源分配判断：确定性规则由程序执行，模型用于语义理解和材料
评审；高价值任务优先处理，额外复核按预算采样。代码保证单次计划有界及每日
提交尝试限额，协调技能负责遵守累计会话处理量。当前没有 token 或美元硬限额、
自动模型路由，也没有全链路计费。用量来自已提交的评审报告，未测费用保留空值。

岗位去重与现成申请包可以减少重复操作的机会，但尚无自动缓存命中率或节省
时间数据。共用信息问题合并是协调技能的行为要求，不能包装成已实现的语义
聚类算法。简历因此优先写代码可核验的队列、去重、限额和采样设计。

## 面试时讲清楚的设计取舍

1. **什么由模型判断，什么必须确定性执行？** 岗位理解与表达没有唯一答案，交给
   模型；权限、版本、重试条件和提交回执用代码约束。模型生成“成功”不算完成。
   这使昂贵的推理聚焦语义任务，每次都必须成立的条件不依赖模型反复判断。
2. **如何知道评审器值得相信？** 冗余扩写不能获奖，但真正增加相关证据的长文本
   应被识别；交换顺序检测不一致。因此不能只测“偏好短文”，也不能只看一个总分。
3. **为什么分开两个评审视角？** 招聘视角判断材料是否有说服力，事实视角核对
   是否有来源。一次模型测试中，前者指出 80% 收入增长缺少上下文，后者识别出
   确认事实只支持“构建 Python 流水线”，这体现两者职责差异。
4. **可靠性如何兼顾成本？** 每十份抽一份是可配置的采样预算，不能保证其余九份
   正确；版本冻结使复核有明确对象。高风险操作仍需事前授权与确定性检查，不能
   用事后抽检替代。未来可根据真实错误分布评估风险分层抽样是否更划算。
5. **为什么不让 Agent 自己持续改 skill？** 一次失败也可能来自事实缺失、评审器
   偏差或浏览器适配。先保存证据、检验根因，再做小修改和独立回归，避免把噪声
   写成越来越多的规则；运行过程和开发过程使用不同职责边界。

可用以下一段口头开场：

> 我做的是一个让 Agent 安全执行不可撤销操作的运行时，用求职投递做案例。
> 设计时我把问题分成三类：该不该申请、
> 材料写得是否合适，以及外部操作能否正确完成。前两类需要模型理解，授权、
> 状态和重试条件则由程序执行。成本上，我让高匹配岗位优先获得处理名额，
> 对额外模型复核采用抽样，同时保留逐次执行校验。我的工程验证覆盖并发、
> 中断和回执缺失，也实际运行了独立材料评审；真实使用中的单位成本和业务
> 效果还需要继续测量。

## 可以引用的证据及其范围

- 六组公开合成对照、十二个独立模型会话完成一次小规模偏差诊断；此次未观察到
  冗余扩写偏好或顺序不一致，也通过了信息劣化和有效扩写对照。不是“消除偏差”。
- 十次模拟投递生成一个持久化样本；两个独立模型会话识别出植入的无来源收入
  数字，报告与告警完成落盘。不是十次真实求职，也不是人类招聘官评价。
- 完整工程回归、隔离的本地浏览器演示与验证记录见 [VERIFICATION.md](VERIFICATION.md)。
- 零安装回放页 `docs/demo/index.html` 由一次真实的本地演示运行生成，可直接发给面试官；
  其中没有运行语言模型，人和岗位都是合成数据，展示的是运行时的执行边界和故障处理。
- 当前没有真实面试率、录用率或吞吐成本提升数据。没有自动统计漂移检测或后台
  告警服务；已有的是当前会话内的抽检、待办、证据追踪与开发期改进流程。

## 下一步最有价值的证据

表达已能展示系统设计与工程验证能力。要进一步增强业务交付说服力，优先补
真实、经授权的使用记录，按照同一任务集和质量标准测量：

| 维度 | 应测量的指标 | 为什么有用 |
| --- | --- | --- |
| 业务完成 | 合格任务的完成率、需人工修正比例、实际节省的人工时间 | 证明解决了用户的问题 |
| 单位开销 | 每个合格完成任务的模型用量、耗时及人工介入时间，计入失败与重试 | 避免只优化便宜的调用而增加返工 |
| 运行稳定 | 工具失败分布、恢复成功率、未知状态滞留时长，以及足量样本上的延迟分布 | 证明机制在实际使用中有效 |

先测基线，再比较一种改动的质量与开销；未知费用不能填零。真实招聘结果受
岗位、市场和个人背景影响，不宜直接归因于 Agent。当前没有这些结果时，保持
上述工程项目定位；不要通过增加“生产级”“高可用”等形容词来替代证据。
