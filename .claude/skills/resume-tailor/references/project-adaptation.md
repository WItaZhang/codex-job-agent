# 按岗位的技术偏好改编项目

从招聘方要交付的工作入手。某个框架出现在核心职责、客户采用目标或明确的加分项中，就追问它对这份工作有什么用；产品介绍里出现一次，通常不足以重写项目。JD 接受同类技术时，能说明同一工程能力的原实现也有价值。JD 明确要求用指定栈做过生产交付时，把实际交付与相邻经验分开评价。

**从业务目标确定可以替换的部分。** 选一个相关项目，弄清谁想完成什么、可用输入、预期输出，以及必须保留的行为。旧架构是理解项目的起点。JD 明显偏好某技术且组件适配时，直接用它重新设计并改写项目段，无需先证明以前用过它。若还想展示历史实操，再查本人确认、源码或旧实验；单凭间接依赖不足以断定本人用过框架。

**把技术放进有理由改的组件。** 指出目标技术接手哪段逻辑、复用哪些接口、相对现有实现带来什么收益或代价。挑一个能区分两种方案的场景，写清预期行为和如何验证；并发、失败重试、延迟、成本或正确性按项目选。两种选型都适用时，按 JD 偏好交付目标栈的版本，记录替换的代价。若目标栈破坏了项目约束，另选更合适的接入点。把关键取舍留在已有的 `requirements.md` 或 `response.md`，简历只取最能说服招聘方的一处。

工程交付岗优先写技术在产品里做的工作。顺着一次用户操作或系统事件找出变化，用项目里的具体对象来写，然后挑一个测试解释这个行为何时仍成立。遇到对照实验，先读两条路径各自做了什么。一条路径本身就展示了岗位要的能力时，可以直接写它的用途；选型或研究才是核心贡献时，再把比较和结论放在前面。

**把结果写成简历里的项目。** 用岗位熟悉的术语重述实际机制。挖到真实使用、比较或原型，就写清本人做了什么、在哪个任务上验证。项目标题和条目都可以直接点名目标技术。正文用准确的动词说明实际完成的工程工作：画出了状态和分支可写 *modeled*，比较过两个实现可写 *compared*，有可运行实现可写 *implemented*。流程图或方案本身也可以是一项成果。内部记录证据和验证状态；简历无需统一加 *proposed* 标签或逐条解释缺了什么。读者应能从措辞准确理解贡献；若一句话会让人以为系统已在运行，就改写具体完成的工作。单纯构思不列作熟练技能。用户要落地原型时，再用真实接口执行对照或故障用例，按实测结果更新措辞。原实现的指标保留在原实验、数据与环境上。
