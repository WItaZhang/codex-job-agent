## 1. 目标和使用场景

本模块只做一件事：给它一份岗位清单，它把每个岗位的申请表填到提交前，然后核对填进去的内容对不对。**它永远不点提交。**

- 输出有两样：每个岗位一个停在提交前的标签页，以及一份逐栏的报告。
- 本模块只按"填进去的内容对不对"来评判。岗位打不开或被门槛挡住，不算填错。但报告要写清楚用户该做什么。
- 起因：2026-10-15 第一批真实投递了 30 个岗位。每个岗位只拿回一个结果码和几行 NOTE，没有逐栏记录。填错的地方全靠用户逐个打开标签页才发现（见决定记录）。所以先把"填表"拆成一个能单独测试的小模块，其他部分以后再接上。

使用场景：

1. **现在（开发和验证）**：用户挑几个真实岗位，写成清单，运行本模块。然后读报告、补标准答案或要求清单，再在录制上重测。直到报告和用户亲手检查的结果一致为止。
2. **以后（接入 /apply）**：/apply 把一批岗位转成清单，交给本模块。用户按报告检查标签页，然后自己提交。自动提交的事以后另定。

每个真实岗位默认只真实访问一次。第一次访问时，本模块把表单录成本地的仿真表单，以后重测都用录制，不再访问网站。这样不会对同一个岗位反复填写，也减少了对网站的访问（用户 2026-10-15 的要求）。

## 2. 输入

| 输入 | 位置 | 谁写 |
| --- | --- | --- |
| 岗位清单 | 任意路径，默认 `data/local/form-fill/lists/` | 用户自己写或请 agent 起草；以后由 /apply 的代码生成 |
| 投递资料 | `data/local/applicant/applicant.yaml`、`profile.json`（spec 4.10，不变） | 用户 |
| 标准答案 | `data/local/applicant/answers.yaml` | 用户。agent 可以起草，每条都由用户确认 |
| 要求清单 | `data/local/applicant/checklist.yaml` | 用户。评审的建议要经用户同意才加进去 |

- 这些文件都在 git 忽略的 `data/local/` 下。
- 项目只提交示例：`docs/examples/applicant/answers.example.yaml`、`docs/examples/applicant/checklist.example.yaml`、`docs/examples/form-fill-list.example.yaml`。
- 开始运行前，代码按 schema 校验这四样。只要有一处不合格，整次都不运行，并说明哪里不对。

### 2.1 岗位清单

```yaml
# 示例，值都是编的
jobs:
  - id: acme-ml-01                  # 清单内唯一；/apply 生成的清单用岗位编号
    url: https://job-boards.greenhouse.io/acme/jobs/1234567   # 申请页地址，必须是 https
    company: Acme Robotics
    title: Machine Learning Engineer
    resume: main                    # applicant.yaml 里的简历 id
    cover_letter: letters/acme-ml-01.txt   # 求职信文本，同名 .pdf 用来上传；相对路径按清单文件所在目录算
  - id: beta-ds-02
    url: https://jobs.lever.co/beta/0f1e2d3c
    company: Beta Health
    title: Data Scientist
    resume: research
    cover_letter: none              # 不交求职信
    revisit: true                   # 已有录制也真实访问一次（见 4.1）
    ignore_filled_on_page: 2        # 只用于可行性验证（6.1 第 8 项）：忽略第 2 页的 checkpoint("filled")
```

- 校验规则：
  - `id` 不能重复；
  - `url` 必须是 https；
  - `resume` 必须在 applicant.yaml 里；
  - 求职信的 .txt 和 .pdf 都要存在；
  - `ignore_filled_on_page` 可选，是正整数。

  有一条不对，整份清单都不运行。
- 清单只说明填哪个岗位、用哪份简历和哪封求职信。选岗位、选简历、写求职信都不归本模块管。

### 2.2 投递资料

沿用 spec 4.10 第 8 条和 §10 第 61、64、69 条：

- `applicant.yaml` 列出简历（PDF 和文本）、`apply_agent_read`、`onsite_ok`、`relocation`。
- `profile.json` 放联系方式和招聘网站的密码。
  - 只有代码会读它，读的时机只有三个：
    1. 准备时（4.1）：检查标准答案引用的字段是否存在，只看有没有。接入 /apply 以后，还要检查它和标准答案重复的部分是否一致（2.3）；
    2. 生成填表指令；
    3. 核对联系方式和打码（4.4、5.6）。
  - 任何 agent 都不能用读文件工具读它。
- 本模块不用 `careful_companies`，因为本模块从不提交。

### 2.3 标准答案（answers.yaml）

这个文件写的是：申请表会问到的每一个事实，以及它唯一正确的答案。代码用它核对事实（5.1）。

- **键和类别**：每条用 `类别.名称` 作键，和意图的 `dimension.key` 一样，同一个键只能有一条。类别是代码里固定的封闭集合：`name`、`contact`、`work_auth`、`education`、`experience`、`availability`、`compensation`、`location`、`eeo`、`screening`。新增类别要走开发流程。
- **联系方式只写引用**：`contact.*` 只能写 `from_profile: <profile.json 里的字段>`，不能写值，写了值就校验不通过。这样联系方式仍然只存在 `profile.json` 里。
- **姓名**：
  - `name.legal` 写 `from_profile`。
  - `name.first` 和 `name.last` 必须有，可以写 `from_profile`，也可以直接写值。姓名不属于 5.6 定义的联系方式。
  - 代码不从全名里拆姓和名，因为中间名和多段的姓会拆错。ApplyPilot 取的是全名的第一个词和最后一个词。
  - 可以另写 `name.preferred`。写着 preferred 的栏用它。
- **地点和搬家题**：沿用 applicant.yaml，写 `from_applicant: relocation`，不在两处各写一份。
- **每条可以有的字段**：
  - `answer`：正确答案。也可以改写 `from_profile` 或 `from_applicant`。
  - `kind`：怎么比较。
    - `text`：忽略大小写、空白和标点。
    - `choice`：比较选项文字，规则同 `text`。
    - `yes_no`：
      - 选项文字以 yes 或 no 开头的，按开头判断。
      - 不这样开头的（例如 "I am authorized to work…"），只认 `accept` 里写的选项原文。对不上就记为"没有标准答案"。
    - `date`。
    - `month`：12/2026、Dec 2026、2026-12 都算同一个月。
    - `number_min`：
      - 从文本里取第一个数字。k 当 1000，忽略 $ 和逗号。
      - 不低于答案就算对。
      - 遇到区间（文本或选项，例如 "$80k–$100k"）：区间包含答案，或者下限不低于答案，算对。
    - `url`。
    - `record`：一段经历，由几个子栏组成。school、degree、major（或 company、title）按 `text` 比较，start 和 end 按 `month` 比较（页面上只有年份时只比年份）。start、end 要写成 2025-09 这样的月份，Present 之类的写法放进这个子栏的 `accept`。
      - 可选的 `city` 只写城市名，不写州和国家（用户 2026-10-17：除非题目要求写 Country）。页面上的值和它一样才算对；逗号前一样、后面多写了州或国家的，算格式与写法；写成别的（包括中文）算错的事实；空着或写 N/A 算缺漏。
    - 联系方式不写 `kind`，由代码按栏比较：
      - `contact.email` 不分大小写；
      - `contact.phone` 只比数字，忽略开头的国家码 1；
      - 住址按街道、城市、邮编分别比较：住址栏里只能有申请人自己的街道、城市、邮编和州、国家，多出别的城市或邮编算错。
      - 州和国家在存下的页上不打码，按文字比较：美国州名和缩写算同一个，United States、USA、United States of America 算同一个；代码认不出的写法记"未审查"，不记错。
  - `accept`：其他也算对的写法，可选。
  - `otherwise`：页面上没有 `answer` 这个选项时应该选哪个，可选。没写时，缺这个选项就按"没有标准答案"处理（5.1）。
  - `asks`：这条回答哪些题，写题目里会出现的英文短语。代码用它把题目对到这一条（4.4）。
    - 常见栏目（姓名、邮箱、电话、学校、专业、起止日期）的写法代码自带，`asks` 用来补充。
    - 两者冲突时 `asks` 优先。
  - `source`：这个事实从哪里来，例如简历里的原句，或者"你某天说的"，可选。以后发现"标准答案本身错了"时，靠它回查。
- **问法不同的题分开记**：同一主题、问法不同的题各占一条，不互相套用。
  - 例如"是否有合法工作许可"和"是否有无限制的工作权（有到期日就答 No）"，答案可以相反；"现在是否需要担保"和"现在或将来是否需要担保"也分成两条。
  - 题目自己写了判断规则的（例如 "Answer No if …"），按题目的规则定这一条的答案。
  - 写 `asks` 时用能区分开的短语。一道题对上不止一条时，按"对题有歧义"报告（3.2），不作答。
  - 例外：一条可以写 `overrides: [其他键]`。它和列出的条目同时对上时，以它为准，不算歧义。用于"题目点名某种情况时答案不同"的题，例如"现在或将来是否需要担保？如果在 F-1/OPT 上请选 Yes"。`overrides` 不能互相指向，代码校验。
- **教育和工作经历逐段写**：每段写学校、学位、专业、起止月份，或者公司、职位、起止月份；城市可选。
  - 每个子栏可以写自己的 `accept`，例如学位写 "M.S."、"MS"。
  - 每个子栏也可以写自己的 `otherwise`：页面上没有原值这个选项时应该选哪个，可以写一个或几个，选其中任何一个都算对。例如下拉里没有原专业时选 Computer Science 或 Computer and Information Science（用户 2026-10-17）。
    - 确认页上看不到下拉的选项，所以填的是 `otherwise` 就算对。
    - 写了 `otherwise` 的子栏，填了原值、`accept` 和 `otherwise` 以外的值，记"未审查"。它可能是要求清单允许的"最相近的选项"，由评审判断。
    - 空着，或停在 "No Response"、"Select One" 这类占位上，算缺漏。
  - 学校可以写 `aliases`（全称、简称），按段对学校时也用（4.4）。
  - 逐段写的原因：表单常常要逐段填，也常常由网站或领英档案预填。
- **和 `profile.json` 重复的事实**：工作许可、薪资、EEO 在 `profile.json` 里也有。本模块只认 `answers.yaml`。接入 /apply 以后，代码在准备时检查两边是否一致，不一致就不运行（4.1）。
  - 只在两边能一一对应的字段上比较。对应表写在代码里，接入 /apply 时一起定。
  - `profile.json` 分不出的区分不比较，以 `answers.yaml` 为准。例如 `profile.json` 的担保只有一项，不分现在和将来。
- **起草**：最初的版本由 agent 起草联系方式以外的条目，然后逐条用选择题请用户确认。联系方式只写引用。
  - 起草的依据：打码后的简历（5.6）和用户说过的话。
  - 打码后的简历用读级工具 `get_redacted_resume` 取（第 9 节）。起草时不读简历原文。

```yaml
# 示例，值都是编的
version: 1
entries:
  name.legal:
    from_profile: personal.full_name
  name.first:
    answer: Alex                             # 姓名可以直接写，也可以写 from_profile
    kind: text
  name.last:
    answer: Example
    kind: text
  contact.email:
    from_profile: personal.email             # 只写引用，不写值
  contact.phone:
    from_profile: personal.phone
  work_auth.authorized_us:
    answer: "Yes"
    kind: yes_no
    asks: ["legally authorized to work in the united states"]
  work_auth.sponsorship_now:
    answer: "No"
    kind: yes_no
    asks: ["currently require sponsorship"]
  work_auth.sponsorship_future:              # 问"现在或将来"的题对到这一条
    # 这道题的答案要你自己补，示例不代表你的情况；它和 sponsorship_now 可以不同
    answer: "<Yes 或 No>"
    kind: yes_no
    asks: ["now or in the future", "in the future require"]
    source: "<谁、哪天、怎么说的>"
  education.ms:
    kind: record
    school: Example State University
    aliases: ["ESU"]
    degree: Master of Science
    major: Data Science
    start: 2025-08
    end: 2027-05                             # 按月份比较
    city: Springfield                        # 可选，只写城市名
    accept:
      degree: ["M.S.", "MS"]
    otherwise:
      major: [Computer Science, Computer and Information Science]   # 下拉里没有原专业时选其中一个
    source: '简历："M.S. Data Science, Example State University, Aug 2025 – Expected May 2027"'
  compensation.expected:
    answer: 95000
    kind: number_min
    asks: ["salary expectation", "desired salary"]
  eeo.hispanic_latino:
    answer: Decline to self-identify
    otherwise: "No"                          # 页面上没有拒答选项时选这个
    kind: choice
    asks: ["hispanic or latino"]
  location.relocation:
    from_applicant: relocation
```

### 2.4 要求清单（checklist.yaml）

要求清单写的是判断类的要求：要不要填选填栏、开放题写得怎么样、格式对不对，以及筛选题按什么规则作答（5.1）。由独立评审逐条检查（4.5）。填表 agent 也拿到这份清单（4.2）。

- 每条有三项：
  - `id`；
  - `rule`：一句话写清楚什么算通过；
  - `level`：不通过时的严重程度，取 `guess`、`missing` 或 `format`（5.2）。
- 清单归用户所有。评审自己发现的问题只算**建议**，在报告里编号列出（3.2）。
  - 用户回"加 <编号>"后，宿主 agent 照建议原文写进 `checklist.yaml`，同时记下 `added`（日期）和 `from`（哪次运行的哪条建议）。
  - 用户没同意的建议不进清单。第一版不设专门的提交级工具。
- 项目示例里放 2026-10-15 那批暴露出来的几条，用户复制后自己改。

```yaml
# 示例
version: 1
items:
  - id: no_hard_breaks
    rule: 粘贴进文本框的简历或求职信，句子中间不能有换行（从 PDF 复制带来的硬换行）。
    level: format
  - id: optional_history_filled
    rule: 选填的工作经历、教育经历、技能栏，简历里有的都要填上。
    level: missing
  - id: open_answers_specific
    rule: 开放题紧扣题目，回答提问的人想知道的那一点；不堆砌经历，只用最有力的一两条简历事实；说明为什么适合这个岗位；简练有力，不写空话。
    level: format
```

## 3. 输出

### 3.1 标签页

- 每个岗位在投递用的 Chrome 里有自己的标签页。填完后停在最后的提交按钮之前。标签页留着，由用户检查、自己提交。
- 遇到门槛的，标签页停在门槛那一页。
- 岗位打开的新标签页或弹窗都算这个岗位的标签页，都留着，报告里列出各自的地址。例如领英的"Apply on company website"、单点登录弹窗。
- 本模块不关闭、不切换任何其他标签页，因为里面可能有用户正在检查的表。

### 3.2 报告

- 每个岗位一份报告，存在 `data/local/form-fill/runs/<运行编号>/<岗位 id>.json`。同一目录下的 `summary.md` 给用户直接打开看。
- 工具返回的也是这份内容。报告文件和工具返回里的联系方式都打码（5.6）。

**逐栏记录**：页面上每一个看得见的填写项占一行，没填的也算。

| 列 | 内容 |
| --- | --- |
| 字段 | 代码给的编号（`p<页>.<序号>`，规则见 4.3）、所在题组和第几段、控件类型、是否必填 |
| 题目原文 | 页面上的题目文字；选择题附上全部选项 |
| 填入值 | 代码从页面读回的值和读回时间。联系方式打码；密码栏只写"已填"，从不读出；上传栏写页面上显示的文件名和实际上传的文件（4.4） |
| 来源 | 标准答案的键 / 简历原句（引出原句）/ 求职信 / 自己推断 / 页面预填 / 来源未录到（5.3） |
| 核对结果 | 对；错（应为……）；没有标准答案；对题有歧义；来源对不上；未审查（代码判断不了、又没有评审的非空栏，例如 agent 自己推断的筛选题和开放题：严重程度为"无"，列进"需要你做的事"，结论最多"检查后可提交"）；评审：清单某条通过或不通过；评审建议；读不出 |
| 严重程度 | 错的事实 / 无依据的猜测 / 缺漏 / 格式与写法 / 无 |
| 改过没有 | 第几轮改的、改前的值；页面不接受；没改的写原因（没有标准答案、要改领英档案等） |

**原因类别**：每个问题带一个原因类别。它是评审的猜测，不是结论，留给以后跨岗位的根因分析用。类别是代码里固定的封闭集合：

| 类别 | 意思 |
| --- | --- |
| `answer_missing` | 标准答案缺这一条 |
| `answer_wrong` | 标准答案本身错了 |
| `mapping` | 题目对错了条目（例如"现在或将来"对成了"现在"） |
| `instruction` | 填表指令导致的（例如 ApplyPilot 的"EEO 一律拒答"） |
| `prefilled` | 网站预填或别处档案带进来的（领英档案、网站解析的简历） |
| `widget` | 控件没填进去或填错了位置（下拉、日期、上传） |
| `copy_format` | 搬运文字时格式坏了（PDF 硬换行） |
| `checklist_gap` | 要求清单没写到（评审自己发现的） |
| `other` | 其他 |

**整体结论**：每个岗位一个。

- **可能已提交**：录制时页面出现了"申请已收到"之类的文字。这一条优先于其他结论，写在报告第一行（5.6）。
- **不符合申请资格**：页面写明不收这类申请人、如实作答会被系统自动拒（例如"不收在读学生和毕业不满 10 个月的人"），填表 agent 停在那一页（5.5）。报告引用它备注里的原文，不再列要补的栏（用户 2026-10-17）。
- **可以提交**：没有问题，每一栏都读得出来。本模块自己不提交，这只表示用户可以提交。
- **检查后可提交**：只剩缺漏或格式与写法的问题，或者有读不出、来源未录到的栏（列出来请用户看），或者评审失败。
  - 没有一栏由代码核对为对时（例如全是联系方式和自己推断的栏），报告写明"没有一栏由代码核对为对，请逐栏看"（用户 2026-10-17）。
- **不能提交**：还有错的事实或无依据的猜测（5.2）。
- **没填完**：要写明是哪一种。可能的种类有：
  - 门槛；
  - 登录或注册失败；
  - 缺标准答案（5.1）；
  - 已下架；
  - 跳到了别的岗位；
  - 只收邮件；
  - 已经申请过；
  - 页面出错；
  - 卡住；
  - 标签页丢失；
  - 程序没跑起来。

评审的建议不影响结论。

**需要你做的事**：编号列出，尽量让用户回一个编号就行。例如：

```
acme-ml-01  不能提交：1 个错的事实
  1) 毕业月份来自领英档案，和标准答案 education.ms.end 不一致。请改领英档案，然后说"重跑 acme-ml-01"。
  2) "Are you Hispanic or Latino?" 没有标准答案，这一栏空着。请补 eeo.hispanic_latino，再在标签页里自己选。
  3) 建议加入要求清单："网站解析简历后自动填的经历，要和简历逐段一致。"（回"加 3"）
  录制：greenhouse-acme-1234567（可重测填写）
```

（示例，值都是编的。）

**本次运行的汇总**：

- 每种结论各有几个岗位。
- 在两个以上岗位出现的同一问题单独列出。"同一问题"指同一个标准答案键、同一条清单或同一个原因类别。
- 第一版只列出来，不做根因分析的流程（第 8 节）。

### 3.3 录制快照

- 每个真实访问过的岗位都留一份录制，包括每页的空表结构、截图、读回值，以及评审拿到的材料。
- 空表和填入值分开存，详见第 6 节。
- 报告里写明录制编号，以及这份录制能重测什么。

## 4. 流程

- 一次运行按清单顺序，一个岗位接一个岗位地做，因为只有一个投递用的 Chrome。
- 一个岗位出错，不影响后面的岗位。
- 真实访问的运行在后台进行，用状态工具查看进度（和 `start_applying` 一样）。

| 步 | 谁做 | 输入 | 输出 | 什么时候停 |
| --- | --- | --- | --- | --- |
| 0 准备 | 代码 | 清单、投递资料、标准答案、要求清单、配置 | 校验结果、运行编号 | 任何一样不合格：整次不运行 |
| 1 开标签页 | 代码 | 岗位地址 | 新标签页；开始录制 | Chrome 连不上：整次不运行 |
| 2 填表 | 填表 agent | 代码生成的填表指令 | 填好的页面；每页的录制和读回；结束时一份结构化结果 | 见 4.2 |
| 3 读回 | 代码 | 每页最后一次 `checkpoint("filled")` 时的读回（没有时用离开这一页之前自动补录的那份），加上结束时对当前页的重新读回 | 每页每栏的题目、控件、选项、读回值、读回时间 | — |
| 4 对题和核对 | 代码 | 读回值、标准答案、`profile.json`、来源声明、简历、求职信、运行记录里的上传路径 | 每栏的对题、事实核对、来源核验、上传核对结果 | — |
| 5 独立评审 | 评审模型（由代码调用，4.5） | 代码整理的评审材料 | 清单逐条结果、问题、建议、原因类别 | 输出两次都不合格：记"评审失败" |
| 6 当场修正 | 代码挑出要改的，修正 agent 动手改，然后再走一遍 3–5 | 修正单 | 改过的页面、改前值 | 修正单为空，或者修正 agent 已经运行了 2 次（4.6） |
| 7 报告和录制 | 代码 | 以上全部 | 报告；录制和它能重测什么 | — |

### 4.1 准备（代码）

- 校验第 2 节的四样输入。检查标准答案引用的 `profile.json` 字段是否存在：只看有没有，不把值交给任何模型。
- 接入 /apply 以后，还要检查 `profile.json` 和标准答案重复的部分（工作许可、薪资、EEO）是否一致，不一致就不运行。只比较能一一对应的字段（2.3）。
- **已有录制**：清单里每个岗位的录制编号由代码从地址算出（6.2）。
  - 不需要再真实访问的情况：这份录制最近一次的结论是以下之一，而清单里又没写 `revisit: true`。
    - 可以提交、检查后可提交、不能提交、可能已提交；
    - 没填完里的已下架、跳到了别的岗位、只收邮件、已经申请过。

    这时本次不真实访问，报告里写"已录制，请用重放重测"。
  - 最近一次的结论是以下之一的，重跑不需要写 `revisit`：门槛、登录或注册失败、缺标准答案、页面出错、卡住、标签页丢失、程序没跑起来。
- 审批：
  - 真实访问的运行由提交级工具启动，每次都要经过宿主的权限弹窗，由用户本人批准。弹窗摘要列出这次要访问的岗位。
  - 只在录制上重放的运行是准备级（第 9 节）。
  - 定时任务不运行本模块。

### 4.2 填表（填表 agent）

- 填表 agent 是无界面的 Claude Code。模型写在配置中，默认和 /apply 一样。它能用的工具和受到的限制见 5.6。
- 填表指令由代码生成，是本模块自己的指令。
  - ApplyPilot 投递指令里的这些部分不再使用：提交、邮件投递、破解验证码、判断地点，以及"EEO 一律拒答"之类的答题规则。
  - ApplyPilot 的表单操作技巧（多页表单、上传、下拉框）可以照抄。vendor 文件不改。
- 指令里给填表 agent 这些内容：
  - 岗位：地址、公司、职位。
  - 标准答案。联系方式由代码从 `profile.json` 填进去，只出现在这份指令里。
  - 所选简历的文本和 PDF。
  - 求职信的文本和 PDF。
  - 要求清单（`checklist.yaml`）的全部条目，供筛选题和选填栏作答时遵守（5.1）。评审仍然独立按它检查（4.5）。
  - 招聘网站的邮箱和密码，用于注册和登录（spec 4.10 第 5 条）。
  - 本模块的规则（5.1–5.5）。
- **上传的文件**：
  - 代码把所选简历和求职信的 PDF 复制到这个岗位自己的上传目录：`runs/<运行编号>/uploads/<岗位 id>/`。
  - 文件名照 ApplyPilot 的写法，因为招聘方看得到文件名。
  - 核对上传时靠目录区分是哪个文件，不靠文件名（4.4）。
- 先核对页面上的职位和公司与清单是否一致。对不上就停下（跳到了别的岗位），在报告里写出页面上的职位。
- 每一页都调用两次 `checkpoint`，每次都带上当前页的地址（Playwright 回复里的 Page URL）：
  - 填之前调用 `checkpoint("blank")`。代码录下空表，并把这一页每栏的编号和题目返回给填表 agent。
  - 填完、点"下一步"之前调用 `checkpoint("filled")`。代码在这时读回这一页（4.3）。
  - 最后一页停在提交按钮之前，同样调用 `checkpoint("filled")`。
  - 网站打开了新标签页或弹窗时，填表 agent 在哪个标签页里，`checkpoint` 就录哪个：代码在这次运行开始后新开的标签页里按地址找，找不到再用上一次 `checkpoint` 的那个（4.3）。
  - `checkpoint` 是本模块自己的 MCP 服务，和 Playwright MCP 一起由填表 agent 的 Claude Code 启动，随它退出。它经 CDP 连投递用的 Chrome，整个运行保持一个连接。
- 代码另外自动补录，不靠填表 agent 调用，防止它忘了调用 `checkpoint`：
  - `checkpoint` 服务在后台每隔一段时间（配置，默认 1 秒）读一次岗位的标签页，只读不改。换页时，上一页最后一次读到的值就是这一页的补录。
  - 所以补录读的是离开这一页之前的值，不是新页的空表；Workday 这类单页应用换页时没有真正的页面跳转，也补录得到。
  - 离开前最后不到一个间隔里填的值可能没录到，所以 `checkpoint("filled")` 仍是主要的读回。
  - `checkpoint` 加自动补录这套做法，要经过 6.1 的可行性验证（第 3、8 项）。验证结果推翻它时，改写本规格。
- 结束时输出一份 JSON（用无界面 Claude Code 的 `--json-schema`），代码按 schema 校验。内容如下：
  - `status`：`filled` / `gate` / `login_failed` / `needs_answer` / `expired` / `wrong_job` / `email_only` / `already_applied` / `page_error` / `stuck`。
  - `gate`：门槛的种类、所在页面、用户要做什么、仲裁条款的第一句。
  - `fields`：每栏的编号、来源类型，以及标准答案的键或简历原句。
  - `notes`：几句说明。

  它说自己"填了什么值"，一律不采用。值以代码读回的为准。
- 停下的条件：
  - 到了最后的提交按钮之前。
  - 遇到门槛（5.5）。
  - 用投递资料的邮箱和密码登录、注册都失败（`login_failed`，5.5）。
  - 缺标准答案（`needs_answer`，5.1）。具体指以下两种情况，留空就进不了下一页。报告列出题目原文和全部选项。
    - 必填的事实题没有标准答案；如果是筛选题，还要没有简历原句、也没有适用的清单条目。
    - 页面上没有标准答案里的选项，又没写 `otherwise`。
  - 岗位已下架。
  - 不是清单上的这个岗位。
  - 只收邮件投递。
  - 页面显示已经申请过。
  - 卡住，由代码判定：同一页（4.3 的页标识）连续 3 次 `checkpoint("filled")` 之后，页面都没有变成新的页，`checkpoint` 就返回 stop。agent 停下，状态记 `stuck`。
  - 超时（写在配置中，默认 900 秒）。
- 以下两种由代码判定，不靠 agent：
  - `tab_lost`：岗位的标签页（含它打开的子标签页）都不见了，或者 CDP 断开。这个岗位记为没填完。做下一个岗位前先重新连 Chrome；连不上，就把剩下的岗位都记为 `tab_lost`。
  - `system_error`：填表 agent 没有起来、一次工具调用都没有，或者运行器出错。判断方法和 spec §10 第 67 条相同。

### 4.3 读回（代码）

- 代码经 CDP 连上投递用的 Chrome，和填表 agent 用同一个浏览器。页面由代码自己读，不经过填表 agent。
- 岗位标签页打开的新标签页或弹窗，也算这个岗位的。判断依据是 CDP `Target.targetCreated` 的 `openerId` 指向岗位标签页。`checkpoint` 录填表 agent 当前所在的那个。
- 页面上有打开的模态对话框（`<dialog>` 以模态打开，或 `aria-modal`）时，对话框以外的部分用户点不到，只读对话框。对话框里什么都读不出时，退回读整页。
- 每页读出每一个看得见的填写项：
  - 题目文字：label、aria 名称、所在题组的标题。
    - 题组的标题优先取题组框里第一段像标题的文字，例如没有关联控件的 label、legend、标题。取不到时，再取题组前面的文字。
  - 控件类型、是否必填、全部选项、页面上的报错提示。
  - 当前值，按控件读：
    - 输入框和文本框：里面的值；
    - 下拉框：选中的文字；
    - 单选和复选：选中的项；
    - `aria-pressed` 按钮组（如 Yes / No 按钮）：按下的按钮。按钮组旁边藏着的原生勾选框不另算一栏。
    - `role=checkbox`、`role=switch`：`aria-checked`；
    - 自定义下拉（如 Workday、react-select）：显示出来的文字；
    - 上传栏：显示的文件名。
  - 密码栏只记"已填"或"空"，不读值。
- 确认页上以文字显示的"题目和值"也读出来，包括：
  - dt/dd、表格行；
  - 以冒号或问号结尾的题目和紧跟的值；
  - "一行两段"：一段题目文字加一段值。这一行要有同样形状的相邻行，或者紧跟在小标题后面。

  题组框里面的说明文字不当作这种题目。
- 不是填写项的东西不算栏，读回时去掉（用户 2026-10-17）：
  - 步骤条，例如 "completed step 1 of 6"、"step 3 of 6"；
  - 空着、又不是必填的控件文字和区块标题，例如 "items selected"、"or"、"Options Expanded"、"Application"、"Work History (Optional) 1"。这类题目下面有值的（例如 "Options Expanded" 里选了 Python），照常保留。
  - 已经存下的页重出报告时，也按同样的规则去掉，编号不变。
- **读回值从哪里来**：多步表单里，点了下一步，前面的页就不在页面上了。所以：
  - 每页的读回值，取这一页最后一次 `checkpoint("filled")` 时代码读到的值。
  - 这一页没有 filled 时的读回，就改用代码自动补录的那份（4.2），报告里注明是补录的。补录的是离开这一页之前的值。
  - 结束时，再把当前页重新读一遍。
  - 报告里注明每页读回的时间。
  - 某一页既没有 filled 时的读回，也没有自动补录，这一页的栏都记为"读不出（未录到）"。
- 读不出的栏记为"读不出"。这是本模块的问题，不是填表的问题。只要有读不出的栏，结论最多是"检查后可提交"。
- **编号规则**：
  - **页的标识**：
    - 先看标题：当前步骤（`aria-current="step"`）的文字；没有时，取对话框或整页里全部标题的文字。地址（不含查询参数）和标题都一样，就是同一页。
    - 页面没有标题时，用栏目结构的指纹（全部题目原文）。
    - 新出现了追问栏、原有的栏都还在时，不算换页。
    - 标题一样、栏目却完全不同（两边各 2 栏以上、没有一栏相同）时，算换页。
    - 退回到见过的页时，沿用原来的页号。
    - 一栏都没有的页（例如岗位介绍页）不编页号。
  - **栏的身份**：由四样组成：页、所在题组（这一栏前面最近的标题）、题目原文、同一题组里同一题目第几次出现。
    - 同一身份第一次出现时分配序号，以后不再改。
    - 后来出现的栏（例如选了 Yes 才出现的追问），取这一页还没用过的下一个序号，并记下 `appeared_after`：它前面最近的、已经编过号的栏。代码看不出是哪一栏触发的，取最近的。
  - 同一页题目原文相同的栏，靠题组和"第几次出现"区分。例如两段 Education 都有 School 栏：编号不同，报告里写明是 education 第几段。

### 4.4 对题和核对（代码）

1. **对题**：把每一栏对到一条标准答案。
   - 用题目原文去匹配各条的 `asks` 和代码自带的常见写法，忽略大小写和标点。`asks` 优先于代码自带的写法。
     - `asks` 的短语要作为完整的词出现在题目里，例如 "location" 不匹配 "relocation"。
     - 整词对不上、代码自带的常见写法也对不上时，再放宽一次：短语里的词按顺序出现、中间一共最多夹 2 个词，也算对上。例如 "years of experience" 对上 "years of engineering experience"（用户 2026-10-17）。
       - 夹在中间的词不能是 not、no、never 这类否定词："currently not require sponsorship" 不算 "currently require sponsorship"。
       - 放宽只用在对题上；分段时判断一个栏名是不是题目，只看整词。
     - 代码自带的常见写法要和题目整句一样才算，例如 First name、Email、Phone、Address、LinkedIn。它们对到 `name.*`，或者 `from_profile` 指向对应字段的 `contact.*` 条目。
     - 题目整句就是 Location、City、Current location 这类写法、又不在经历段里的，对到 `from_profile` 指向城市的那条（用户 2026-10-17）。"Preferred location" 这类问偏好地点的题不算。
   - 能匹配上几条时，取匹配到的最长短语，因为它最具体。例如 "now or in the future" 比 "require sponsorship" 更具体。
   - 最长短语一样长，却对到不同的条目时，不选任何一条，记为"对题有歧义"，交给评审确认。`overrides`（2.3）不受最长短语的限制：一条和它列出的条目同时对上时，就以它为准。
   - 重复的段落（几段教育、几段工作）：
     - **分段**：按栏名把连续的栏归成一段。学校、学位、专业是学历段，公司、职位是工作段，起止日期、城市、描述跟着所在的段。同一个栏名在段里再次出现，就是下一段开始。段外的栏照常对题。
       - 栏名命中了某条的 `asks`，就按题目对，不算段里的栏（`asks` 优先）。
       - 段中间夹着一栏别的题（例如 Workday 的 "Overall Result (GPA)"），段不断；连着两栏别的题，段就结束。
     - **对段**：先按学校名（含 `aliases` 和这一子栏的 `otherwise`）或公司名，把整段对到一条 `record`，段内各栏再按栏名对。段里的值等于学校名或公司名，或者把它当作完整的词包含在内，都算对上。例如 "百度（Baidu）" 对到别名 Baidu，再比较公司名，判为写错。
       - 整页一起对：先对值和名字完全一样的段，再对包含名字的段。
       - 同一所学校或公司有几条 `record` 时，按段里其他栏（学位或职位、起止）对上得多的那条算。先让只对得上一条的段各取各的，剩下的再分；还分不出时记"对题有歧义"，这几条都不算少了的段。
       - 学校或公司空着、停在占位上的段，按其他栏去对还没用上的那条；对上了，学校或公司那一栏算缺漏。
       - 整段什么都没填的，算"空着的一段"，不算错的事实。
     - **多出来的段**：对不上任何一条 `record` 的段，是标准答案里没有的经历，记为错的事实（用户 2026-10-17）。例如领英把助研填成了工作经历。标准答案按简历逐段列出了全部经历（决定 12）。
     - **少了的段**：页面上有这一类的段，却少了标准答案里的某一段，记为缺漏。
   - 填表 agent 声明了标准答案的键，而代码没对上或对题有歧义时：照它声明的键核对，同时把这个对应作为"待确认的对应"交给评审，不说是谁提出的（4.5）。
   - 代码对上的键和 agent 声明的键不一样时，也按有歧义处理。
   - 评审认可的题目写法，作为"建议加进 `asks`"，和清单建议一样在报告里编号列出（2.4、3.2）。
     - 用户回"加 <编号>"后，宿主 agent 把这个短语写进对应条目的 `asks`。
     - 用户没同意的不加。
2. **核对事实**：对上的栏，按 `kind` 比较读回值和标准答案（2.3、5.1）。联系方式由代码直接和 `profile.json` 比较，值不交给任何模型。
   - 对上了标准答案、页面上却空着的栏，算缺漏。答案是 Yes 的勾选框没勾，也算缺漏；答案是 No 的勾选框没勾，算对。
   - 空着包括停在占位上，例如 "No Response"、"Select One"、"No Selection"、"-- Make a Selection --"、"N/A"。Yes/No 题停在这类占位上也算空着，不算答了 No。
   - 勾选框只看勾没勾：没勾是 No，勾上是 Yes，不管旁边写的是什么字。
   - 代码读不出的日期、月份、起止，记"未审查"，不记错。
   - 意思相同的写法（用户 2026-10-17）：
     - 选项末尾的括号里是地名（国家或美国的州，例如 "I prefer not to disclose (United States of America)"），整句对不上时去掉这个括号再比一次。括号里是别的内容的不去掉，因为它常常就是选项之间的区别（"Master's Degree (in progress)" 和 "(completed)"）。`otherwise` 也这样比。
     - 问"怎么知道这个岗位"这类题，"<岗位的公司名> Careers Website" 和 "Company website" 算同一种写法。比较时：
       - 末尾的括号去掉；
       - 公司名当作 company，公司名里的 Inc、LLC 这类词不算，名字也可以只取前面几个词（"Perplexity AI" 对 "Perplexity Careers Website"）；
       - careers、jobs 这类词不算；website、page、portal 都当作 site。
   - 没对上标准答案、页面上空着的栏，记"没有标准答案"；其中必填的算缺漏，单独列出（不填交不了）。
3. **核验来源**：
   - 标准答案：声明的键必须存在。
   - 简历原句：去掉多余空白后，必须原样出现在所选简历的文本里。
   - 求职信：必须和求职信文本一致，换行可以去掉。
   - 核验不过的，记为"来源对不上"，严重程度和"无依据的猜测"相同。
4. **核对上传**：
   - 期望值由代码按清单得出：所选简历的 PDF、求职信的 PDF。
   - 代码从填表 agent 的完整运行记录（`logs/`，只有代码读）里，取 `browser_file_upload` 实际上传的路径，看它是不是这个岗位上传目录里对应的文件。
   - 页面上显示的文件不是本模块上传的（例如领英存的旧简历），记为错的事实，原因类别 `prefilled`。
   - 必填的上传栏空着，记为缺漏。
5. **代码能判断的格式**：长文本里句子中间的换行，即一行没有以句号、冒号等结尾就换了行。代码先把它们查出来，交给评审，并在报告里列出。级别按要求清单里对应的那一条定。

### 4.5 独立评审（评审模型）

- 每一轮都开一个新的评审。它看不到填表 agent 的指令、过程、备注和自述，也看不到上一轮评审的输出。
  - 填表 agent 也拿到要求清单（4.2），这不影响评审的独立性。评审看不到的是填表 agent 的指令、过程和自述，不是清单本身。
- **评审由代码直接调用**：
  - 代码调用 `structured(prompt, schema)`。
  - 后端是本模块新写的：无界面 Claude Code，加 `--tools ""`、`--strict-mcp-config`、空的 MCP 配置和 `--json-schema`。
  - 模型写在 `form_fill.reviewer_model`，不弱于填表 agent 用的模型。
  - 代码里现在只有 fake 和 host（不调用模型）两种后端（`llm.py`）。
  - 这样做偏离了 spec 5.4 的两处："独立运行模式以后再做"，以及"对话中由宿主 agent 传入理解结果"。
    - 原因：评审必须看不到上下文，要在后台运行、每轮新开，而且修正和再评审在同一次运行里来回进行。
    - 代价是评审只能用 Claude。填表本来就固定用 Claude Code。
  - 测试用 fake client。
  - 宿主 agent 不做评审，因为它看过对话和填表结果，不算"没有上下文"。
- 评审拿到的材料由代码整理：
  - 岗位的公司、职位、地址。
  - 每页每栏：编号、题目原文、选项、是否必填、读回值、代码的核对结果。
  - 来源：只给代码核验过的，即存在的标准答案键、原样出现在简历里的原句、和求职信一致的文字。
    - 不说是谁声明的。没核验过的写"没有声明来源"。
    - 来源本来是填表 agent 声明的。这样给，评审仍然拿不到填表 agent 的上下文。
  - 需要它确认的题目对应，同样不说是谁提出的。
  - 所选简历的文本和求职信文本。简历先由代码打码（5.6）。spec 3.3 要求打码，但代码里还没有实现，`get_resume` 现在返回原文。
  - 要求清单和原因类别表。

  联系方式一律打码，包括对到 `contact.*` 的栏的全部选项（5.6）。

  第一版不给评审截图。截图里有联系方式，给图片打码不如给文字打码可靠；格式问题从读回的文字也能看出来。
- 评审输出以下内容，按 schema 校验：
  - 清单逐条：通过 / 不通过 / 不适用，涉及哪些栏，一句理由。
  - 没对上标准答案的栏：属于事实题、开放题、选填段落还是其他；填的值有没有依据。
  - 题目对应的确认：成立或不成立。
  - 问题：哪一栏、严重程度、对应的清单条目（或标为"建议"）、哪里不对、原因类别。
    - 有确定的正确值时，写出正确值和依据。
    - 依据可以是标准答案的键、简历原句，或者代码能算出的改法（如去掉句中换行）。
  - 建议：可以加进清单的新条目原文。
- 代码的事实核对结果优先。代码判错的栏，评审不能改判为对。
- 评审说某栏和简历矛盾时，必须引出简历原句。代码核验原句确实存在后，才记为错的事实。
- 评审输出不合格时重试一次。再不合格，这一轮记为"评审失败"，结论最多是"检查后可提交"。

### 4.6 当场修正（最多 2 轮）

- 代码从问题里挑出有**确定正确值**的，组成修正单。包括三类：
  - 对上了标准答案、核对结果为错的事实。
  - 页面上空着，但标准答案或核验过的简历原句里有内容的缺漏。
  - 代码能算出改法的格式问题，例如去掉句中换行。
- 以下问题只报告，不改：
  - 没有标准答案的。
  - 开放题写得好不好。
  - 要改领英档案或其他网站才能改的。
  - 页面不接受的：上一轮已经改过、读回值仍不等于正确值的栏，标为"页面不接受"，下一轮不再列入修正单。
- 修正由修正 agent 动手，不由代码直接把值写进页面。因为自定义控件要点击才能改，代码直接写进去的值常常不被网站接受。
  - 修正 agent 是一个新的填表 agent，在同一个标签页里改。
  - 它只拿到修正单：页、栏、题目、正确值。工具限制和填表时一样。
  - 多页表单可以退回前面的页去改，改完照样调用 `checkpoint`。
- 改完后，代码重新读回、重新核对，再交给一个新的评审。改前值写进报告。
- 修正单以外的栏被改动了，要记一个问题："改了不该改的栏"，并写出改前值。
- **计数**：
  - 修正 agent 最多运行 2 次，评审最多 3 次（初评 1 次，每轮修正后各 1 次）。
  - 修正 agent 超时或出错时，这一轮照样计数，按读回结果评审。
  - 改的过程中遇到门槛，就停止修正，结论按门槛处理。
  - 每轮修正有自己的超时（配置 `form_fill.fix_timeout_seconds`），不占 4.2 的超时。
- 修正单为空，或者修正 agent 已经运行了 2 次，就停。剩下的问题照常报告。

### 4.7 报告和录制（代码）

写好报告（3.2），收好录制（第 6 节），标签页留着不关，然后做下一个岗位。全部岗位做完后，写本次运行的汇总。

## 5. 规则

### 5.1 对的标准

- **事实**：姓名、联系方式、日期、学历、工作许可、EEO 等。读回值和标准答案按 `kind` 比较一致才算对，由代码判断。
- **判断项**：要不要填选填栏、开放题写得怎么样、格式。由评审按要求清单逐条判断。
- 填入值一律是代码从页面读回的值，不用填表 agent 的自述。
- **没有标准答案的事实题**：不猜，一律空着。筛选题先按下一条的顺序作答，三样都没有时才按这一条处理。
  - 选填的空着；必填的也空着。
  - 必填题留空进不了下一页时，停在这一页，状态记 `needs_answer`，结论是"没填完：缺标准答案"。报告列出题目原文和全部选项，写"需要你补标准答案"。
  - 用户补好后，可以在标签页里自己填，也可以说"重跑 <id>"，从这一页接着做（5.5）。
  - 页面上没有标准答案里的选项、又没写 `otherwise` 时，同样处理。
- **筛选题**（技能和经验题，例如"用过 X 吗"；薪资题）按这个顺序作答：
  1. 标准答案；
  2. 简历原句；
  3. 要求清单里适用的作答条目。
     - spec 4.10 第 5 条照 ApplyPilot 答这类题的规则，例如同领域的工具答 YES、按岗位薪资区间的中点报薪资，不是本模块的填表规则。
     - 用户要用这些规则，就写成自己要求清单里的条目，由评审判断。用户也可以在清单里写"只按简历答"。
     - 按清单条目作答的栏，来源记为"自己推断"。评审判定它符合那一条的，不算无依据的猜测（5.3）。
  4. 三样都没有时，按上一条"没有标准答案的事实题"处理：空着，必填的留空进不了下一页就记 `needs_answer`。

  薪资题代码只检查不低于 `compensation.expected`（`number_min`，2.3）。

### 5.2 严重程度

从重到轻：**错的事实 > 无依据的猜测 > 缺漏 > 格式与写法**。

| 级别 | 例子 | 对结论的影响 |
| --- | --- | --- |
| 错的事实 | 毕业月份和标准答案不一致；页面上多出一段标准答案里没有的经历；"现在或将来"的担保题按"现在"那条作答，而两条答案不同；上传的不是清单指定的简历 | 只要有一条，这个岗位就**不能提交** |
| 无依据的猜测 | 族裔题没有标准答案，填表 agent 自己选了一项；来源对不上 | 只要有一条，这个岗位也**不能提交**。事实题上的猜测和错的事实一样，可能成为虚假陈述 |
| 缺漏 | 选填的教育经历、工作经历空着；必填项空着；下拉停在 "No Response" | 检查后可提交 |
| 格式与写法 | 粘贴的简历带着 PDF 硬换行；开放题写得空泛、不具体 | 检查后可提交 |

- 开放题写得空泛、不具体，默认算格式与写法。示例清单的 `open_answers_specific` 就是这一级。
- 判断项的级别以对应清单条目里用户写的 `level` 为准（2.4、4.4）。
- 开放题里和简历矛盾的内容不在此列，按 4.5 记为错的事实。

### 5.3 来源

每个非空的栏都要写来源。来源有以下几种：

1. **标准答案**：写键，例如 `work_auth.sponsorship_future`。
2. **简历原句**：引出原句。
3. **求职信**。
4. **自己推断**：用在开放题上是正常的，由评审按清单判断；用在事实题上，就是"无依据的猜测"。筛选题按要求清单的条目作答、评审判定符合那一条的，不算无依据的猜测（5.1）。
5. **页面预填**：由代码判定，不看 agent 的声明。某栏在 `checkpoint("blank")` 时已经有值，到 `checkpoint("filled")` 时值没变，来源就记为页面预填。这种栏照样按标准答案核对。
   - 单列这一种的原因：领英档案和网站解析的简历带进来的值不是填表 agent 写的，归到"自己推断"会误导；agent 自己也未必知道哪些值是预填的。

第 1–4 种由填表 agent 声明，由代码核验（4.4）。非空的栏如果没有声明来源、也不是页面预填，按"自己推断"处理。

例外：某一页没有 `checkpoint("blank")` 时的录制，就判定不了页面预填。这一页没声明来源的非空栏记为"来源未录到"，不按"自己推断"处理。

- 事实照样由代码核对。
- 和读不出一样，这是本模块的问题。有这种栏时，结论最多是"检查后可提交"。

### 5.4 修正的边界

- 只改有确定正确值的（4.6），最多 2 轮，每一处都写下改前值。
- 不改别的网站：领英档案、邮箱、招聘网站的个人资料页都不改，只在报告里写用户要去改什么。
- 领英快速申请弹窗里能直接选的栏（例如邮箱下拉）算本页的栏，可以改。
- 不改修正单以外的栏。

### 5.5 门槛

不设网站白名单，什么网站都可以试。遇到下表的情况时：停在那一页，标签页留着，报告里写明**用户具体要做什么**。用户做完后说"重跑 <id>"。

| 门槛 | 报告里写什么 |
| --- | --- |
| 单点登录（Google、Microsoft、Apple、Okta 等） | 在投递用的 Chrome 里，用哪个账号登录哪个网站 |
| 邮件验证码或验证链接 | 去哪个邮箱找哪个网站发来的邮件；本模块不读邮箱 |
| 人机验证（captcha） | 在哪一页手动完成；本模块不破解 |
| 仲裁协议 | 条款第一句原文；永远不接受，投不投由用户决定 |
| SSN 或其他身份证号 | 哪一栏要求填；永远不填 |
| 付款、申请费、银行卡 | 哪一页要求；永远不填、不付 |
| 摄像头、麦克风、证件照、人脸验证 | 哪一页要求；永远不授权 |

- **注册和登录**：沿用 spec 4.10 第 5 条。先用投递资料里的邮箱和密码登录公司自己的招聘网站，失败就用同一组邮箱和密码注册。注册后要邮件验证的，按门槛处理。
- **登录失败**：登录和注册都失败、又不是上面的门槛时，停下，状态记 `login_failed`。例如网站提示账号已存在，可密码不对。
  - 报告写明是哪个网站、页面上的报错原文。
  - 报告写明用户可以怎么做：在投递用的 Chrome 里自己登录后说"重跑 <id>"；或者在这个网站用投递资料的邮箱重设密码，自己把新密码写进 `profile.json`。
  - 2026-10-15 那批 30 个岗位里有 4 个是这种情况。
- 以下情况既不算门槛，也不填：
  - 岗位已下架；
  - 跳到了别的岗位；
  - 只收邮件投递：本模块从不发邮件，报告里写出邮箱地址；
  - 页面显示已经申请过。
- **重跑**：
  - 代码在运行记录里存下这个岗位标签页最后的地址和 CDP 标签页编号。
  - 重跑时先按编号找；找不到再按地址找，因为 Chrome 重启后编号会变。
  - 还是找不到，就重新打开岗位地址，从头做。
  - 重跑算一次真实访问，录制里另存一份（6.2）。
- 本模块不判断地点资格，也不挑岗位，清单上有的就填。
- **不符合申请资格**：页面写明不收这类申请人、如实作答会被系统自动拒的（例如不收在读学生），填表 agent 停在那一页，用 "NOTE:" 引用原文，结果是 `not_eligible`，结论是"不符合申请资格"（3.2）。ApplyPilot 原有指令里给工作许可用的 `not_eligible_work_auth` 也算这一种。永远不编一个不真实的答案去过这道题（用户 2026-10-17）。这不是挑岗位：岗位照样在清单上，投不投由用户决定。

### 5.6 隐私与安全

- **永远不点最后的提交按钮。** 在真实网站上，代码拦不住点击。所以靠三样东西：
  - 填表指令。
  - 每页录制时的检查：页面出现"申请已收到"之类的文字时，结论为"可能已提交"，写在报告第一行。
  - 重放测试（6.4）。
- **填表 agent 的工具**：
  - 只有浏览器：Playwright MCP（固定 0.0.83）经 CDP 连投递用的 Chrome，再加本模块的 `checkpoint`。`checkpoint` 只触发代码录制，返回这一页的栏目编号（卡住时返回 stop），不能读写文件。
  - 没有 Gmail。邮件验证码按门槛处理（5.5），本模块也从不发邮件。
  - 多了 `checkpoint`、没有 Gmail，这两点是本模块对 spec 4.10 第 6 条（"投递 agent 只有浏览器和 Gmail（读、搜、发信）"）的例外，只对本模块。CLAUDE.md 的投递条款已写明填表 agent 的放行更窄。/apply 不变。
  - 不能用 `browser_run_code_unsafe`。
- **投递用 Chrome 里的个人标签页**：填表 agent 和用户共用这个 Chrome。"不碰原来开着的标签页"只是写给它的指令，拦不住它读。所以启动前，代码列出开着的这类网站的标签页，只写网站的地址，提醒用户关掉；只提醒，照样启动（用户 2026-10-17）：
  - `apply.blocked_origins` 里的网站和它们的子域名（邮箱、银行、支付、密码管理）；
  - 学校系统：域名里有 edu 这一节的（.edu、.edu.cn）；
  - 清单上岗位地址所在的网站不算。
  - 查标签页时不为此启动 Chrome。Chrome 还没开时，提醒里写明"没能检查"。
    - Playwright MCP 的说明写明，它在服务进程里执行任意 JavaScript，等同于在本机执行任意代码，和"没有命令行"冲突。
    - 做法：在 `form_fill.disallowed_tools` 里写 `mcp__playwright__browser_run_code_unsafe`，经 `--disallowedTools` 传入。
    - 现在的 `apply.allowed_tools` 用 `mcp__playwright` 放行了整个服务。这个工具在 0.0.83 里不需要 `--caps` 就有，所以现在是放行的。
    - 2026-10-15 那批 30 个岗位里，有 13 个用了它，共 108 次。
    - 禁用后如果有某类控件填不进去，由本模块的代码提供一个范围很窄的辅助工具，不重新放开它。
  - 同样禁用 `browser_close`、`browser_network_request`、`browser_network_requests`。前一个会关掉用户正在检查的标签页；后两个会把带 Cookie 的请求头交给模型，进而写进运行记录。
  - 不跳过权限检查，只预先放行上面这些工具。没有内置工具，不能写文件。读文件只限 `apply_agent_read` 列出的目录，以受限模式运行（spec §10 第 55、64 条）。
  - 浏览器打不开的网站名单沿用 `apply.blocked_origins`。
- **联系方式**：这里指邮箱、电话、住址和个人主页链接。
  - 只在填表指令里出现，由代码从 `profile.json` 填入。
  - 评审、宿主 agent、报告、录制和运行记录里一律打码。
    - 打码的写法：邮箱只留域名，电话只留最后两位，住址不显示，个人链接只显示网站名。
    - 核对由代码做。
  - **打码两种方式都做**：
    1. 和 `profile.json` 的值比较。比较前先规范化：电话只比数字，邮箱不分大小写，住址按街道、城市、邮编分别比。
    2. 按格式和栏目：任何形如邮箱、电话号码的文字，以及对到 `contact.*` 的栏的值和全部选项，一律打码，不管是不是 `profile.json` 里的值。

    第 2 种的起因：
    - 领英快速申请的邮箱下拉，列的是领英档案里的邮箱，不一定在 `profile.json` 里；
    - 登录后的页面，在填之前就带着预填的联系方式和页头的账号邮箱。
  - **填表 agent 的完整运行记录**（`runs/<运行编号>/logs/`）：代码写入时就按上面两种方式打码，密码写成"已填"。
    - 这样 Claude Code 和 Codex 两个宿主都不靠读文件拒绝规则来保护它。Codex 没有对应的读文件拒绝规则（`.codex/config.toml` 只管工具确认）。
    - Claude Code 下另在 `.claude/settings.json` 的 deny 里加 `Read(./data/local/form-fill/runs/*/*/log.jsonl)`（运行记录在 `runs/<运行>/<岗位>/log.jsonl`），作为第二层。
    - 打码不影响上传核对要用的路径（4.4）。
  - 任何 agent 都不能用读文件工具读以下文件：
    - `profile.json`、`.env`；
    - 填表 agent 的完整运行记录。
  - 录制里不存联系方式的明文，也不存密码：
    - 保存前，代码按上面两种方式打码：和 `profile.json` 相同的文字换成引用，例如 `{{personal.email}}`；其余按格式打码。
    - 截图里，代码按页面元素找出显示命中文字的元素，截图时给这些元素本身加样式涂黑。样式跟着元素走，所以对话框这类浏览器顶层元素里的也能涂到；盖在页面上的遮罩盖不到顶层元素。涂黑失败的截图不保存，记为"截图未存：打码失败"。
    - MHTML 是编码过的整页，按文字替换处理不到。代码按 MIME 拆开，逐段解码、打码后写回；写回后的文件打码扫描仍有命中，就不存 MHTML，只存简化 HTML 和截图（6.1 第 6 项验证）。
    - 密码栏从不读值。
- **简历**：交给评审之前由代码打码。先按 `profile.json` 的联系方式逐项替换，再用通用的邮箱、电话格式兜底。spec 3.3 要求这样做，但代码里还没有实现，本模块新写这个函数。起草标准答案用的 `get_redacted_resume`（第 9 节）也用它。
- **页面内容不可信**：页面上写给 AI 的话，填表 agent 和评审一律不理。评审材料里的页面文字要标明是数据。
- **审批**：真实访问的运行是提交级，每次都由用户本人在宿主弹窗里批准，不得设为"总是允许"。定时任务不运行本模块。

### 5.7 模型输出校验

- 填表 agent 结束时的 JSON 和评审的输出，都按 schema 校验：
  - 状态、门槛种类、来源类型、严重程度、原因类别、结论都是封闭集合。
  - 栏目编号必须是代码读回过的。
  - 标准答案的键和清单条目的 id 必须存在。
  - 简历原句必须核验通过。
- 不合格时：
  - 评审重试一次（4.5）。
  - 填表 agent 的 JSON 不合格时不重试，因为重试要再访问一次网站。全部来源按"没有声明"处理（页面预填仍由代码判定），事实照样由代码核对。
- 模型无关：评审走 `structured(prompt, schema)`（后端见 4.5），填表走无界面 Claude Code（和 /apply 是同一个后端）。核心逻辑的测试只用 fake client。

### 5.8 反复出现的问题

同一个问题在多个岗位上反复出现时，要做根因分析，由用户选择怎么改。选项有：改标准答案、改要求清单、改填表指令、改代码、提意见，或者这次不改（不携带任何信息）。第一版只在汇总里列出这些问题（第 8 节）。

## 6. 录制与重放

### 6.1 先验证能不能录（切片第一步）

Playwright MCP 0.0.83 有 `--save-session` 和 `--output-dir`，但不能录 HAR。它的 `--caps=devtools` 里有 trace 和录像工具，但这些工具要由 agent 自己调用，录下来的也不是每页的栏目结构。所以录制由本模块自己的代码来做：经 CDP 端口（ApplyPilot 的 9222 加 worker 编号）连上投递用的 Chrome，一页一页地录。

**谁来操作**：模块还没做出来，所以验证时用一个最小的填表 agent。

- 这个 agent 用现有 /apply 的无界面 Claude Code 和 Playwright MCP 配置，去掉 Gmail，按 5.6 经 `--disallowedTools` 禁用 `browser_run_code_unsafe`，加一个最小的 `checkpoint`。指令只要求填到提交前。
- 不由你在投递用的 Chrome 里手动操作、代码只录，因为那样测不了第 1、3 项。
- 每个岗位只访问一次。开始前在对话里列出这 3 个岗位，等你同意。

先用 3 个真实岗位验证：一个 Greenhouse 或 Lever 单页表、一个 Workday、一个领英快速申请。每一项的判定标准如下：

1. **不干扰 Playwright MCP**：代码作为第二个 CDP 客户端连上之后，Playwright MCP 的 `browser_tabs` 列表和连上之前一致；之后一次点击和一次 `browser_file_upload` 都成功（页面上显示了文件名）。先试 Playwright 的 `connect_over_cdp`；有干扰就改用原始 CDP。
2. **认得出标签页**：代码定位到的标签页地址，要和填表 agent 正在操作的一致。翻页、跳转之后，以及网站打开新标签页或弹窗之后（`Target.targetCreated` 的 `openerId` 指向岗位标签页），都要满足这一条。
3. **`checkpoint` 能用**：在时限内（暂定 5 秒，写进配置）返回，带上这一页的栏目编号。
4. **读回覆盖这些控件**：原生控件、Workday 的自定义控件、react-select、单选和复选题组、上传栏、嵌在公司网站里的表单（iframe）。
   - 对照截图，逐栏比较读回值和页面显示。
   - 单页表读不出的栏要为 0。
   - Workday 和领英列出读不出的栏数和是哪些，由你决定能不能接受。
   - 列出禁用 `browser_run_code_unsafe` 后填不进去的控件，作为要不要提供窄辅助工具的依据（5.6）。
5. **存得下这些内容**，每样文件都存在且不为空：
   - 整页 MHTML（CDP `Page.captureSnapshot`）；
   - 整页截图；
   - 去掉脚本的简化 HTML；
   - 这一页加载时的 GET 响应（去掉 cookie 和认证头）。
6. **打码生效**：
   - 由代码检查。代码读 `profile.json`，只报告命中次数。
   - 查的内容：`profile.json` 的每一项联系方式（含规范化后的写法），以及页面上出现过的其他邮箱、电话。
   - 查的位置：读回值、选项、简化 HTML、MHTML、网络记录。这些地方都要命中 0 次。
   - 截图由你看一遍涂黑。
   - MHTML 打码做不到时，改成不存 MHTML。
7. **重放自检**：至少一个单页表通过 6.3 的重放自检。
8. **换页时自动补录**：在多步表单的某一页，让代码忽略这一页的 `checkpoint("filled")`（清单里写 `ignore_filled_on_page`，2.1），相当于填表 agent 填完后没调用就翻了页。
   - 补录拿到的必须是离开前这一页的填入值，和截图一致，不是下一页的空表。
   - Workday 这类单页应用里的换页也要补录得到。

结果写成"岗位 × 项目：通过 / 不通过 / 现象"的表给你看，然后再做后面的部分。任何一项不通过，先回来和你商量，例如去掉 `checkpoint`，只靠代码按页面变化录制。

验证结果可能推翻录制的触发方式（4.2、4.3：`checkpoint` 加页面跳转时自动补录；第 3、8 项）和重放以哪种做法为主（6.4；第 7 项）。推翻时，先改写本规格，再做后面的部分。

### 6.2 录什么、存在哪里

```
data/local/form-fill/
  lists/                        清单（也可以放在别处）
  runs/<运行编号>/
    <岗位 id>.json              报告
    summary.md                  汇总
    logs/<岗位 id>.jsonl        填表 agent 的完整运行记录（写入时已按 5.6 打码，agent 不能读）
    uploads/<岗位 id>/          这个岗位上传用的简历和求职信 PDF
  recordings/<录制编号>/
    meta.json                   地址、公司、职位、平台、录制日期、页数、能重测什么、最近一次的运行和结论
    form/                       空表（填之前录；只有结构，不存值）
      p1.structure.json         每栏：编号、题组、题目原文、控件、必填、选项
      p1.mhtml                  整页，给人看（打码做不到时不存）
      p1.html                   去掉脚本的简化页面
      p1.png                    截图（联系方式涂黑）
      network.json              第一页加载时的 GET 响应（去掉 cookie 和认证头），给重放用
    fills/<运行编号>/           某一次填写（和空表分开存）
      state.json                页的标识和每页的编号表（代码接着编号用）
      checkpoints.json          每次 checkpoint：阶段、页号、填表 agent 给的地址、代码读的标签页的地址、用时
      requests.json             非 GET 请求：只记方法和去掉查询参数的地址，不存内容（6.4 用）
      p1.prefilled.json         blank 时页面上已有的值（联系方式按 5.6 打码）
      p1.values.json            最后一次 filled 时每栏的读回值和读回时间（联系方式按 5.6 打码）
      p1.auto.json              后台补录的这一页最后一次读到的值（同样打码）
      p1.filled.html            填完时的简化页面（同样打码；读回值以 p1.values.json 为准）
      p1.filled.png             截图（联系方式涂黑）
      final.json                填表 agent 退出后对当前页的重新读回
      round1/ round2/           每轮修正后的读回
      filler_output.json        填表 agent 的结构化结果（来源声明）
      review_input.json         每轮评审拿到的材料
      review_output.json        每轮评审的输出
```

- 这些都在 git 忽略的 `data/local/` 下。
- **录制编号**：由代码从规范化后的地址生成。
  - 规范化：host 小写，去掉查询参数里的跟踪字段。
  - 已知平台（greenhouse、lever、ashby、workday、linkedin）：取平台名、公司和岗位号，例如 `greenhouse-acme-1234567`。
  - 其他网站：用 `other-<host>-<地址哈希前 8 位>`。
- `form/` 只存题目、控件、选项、必填、位置。`checkpoint("blank")` 时页面上已有的值（网站或领英预填的）不存进 `form/`，存在 `fills/<运行编号>/p<n>.prefilled.json`。
- 网络记录的规则：
  - 只存第一页加载时 GET 请求的响应。非 GET 请求只记方法和地址，不存内容。
  - 地址或内容里有联系方式（按 5.6 的两种方式判断）的请求，整条丢掉。
  - 需要登录的页面不存网络记录，例如 Workday 的账号页和领英。代码这样判定：运行结束后，只有一页、没出现过密码栏、也没有一条响应带着联系方式（说明是登录后的页面）的录制，才留下 `network.json`，其余删掉。多步表单本来就只能重测核对（6.3），用不上网络记录。
- 同一个岗位再次真实访问时：表单没变，就只多一份 `fills/<运行编号>/`；表单变了，就另存一份 `form-v2/`。
- 录制全部保留，不自动删除，由用户自己删。每页的 MHTML 加截图大约几 MB。

### 6.3 每份录制能重测什么

由代码自动判断，写进 `meta.json`，不手写。分两类：

- **可重测填写**：要同时满足三条：
  - 单页表单；
  - 没有跨域 iframe；
  - 通过重放自检：代码在重放页面上读出空表结构，和录下的空表结构逐栏一致（题目、控件、选项、必填；不比较值）。

  预计大多是单页的 Greenhouse、Lever、Ashby 表单。它们的下拉多是脚本控件，所以能不能重测以自检结果为准。
- **只能重测核对和评审**：多步、靠脚本和接口驱动的表单（Workday、领英快速申请），以及自检没通过的。可以用存下的读回值、简化页面和评审材料，重测第 3–5 步和报告。

不管属于哪一类，每份录制都保存了每页的结构、截图和读回值。

### 6.4 重放

- 代码在本机起一个只监听 127.0.0.1 的小服务，端口写在配置中。
- 重放用一个干净的浏览器，不带日常 Chrome 的登录状态。
- 重放页面有两种做法：
  - **网络回放**：按 `network.json` 返回录下的响应，页面脚本照常运行。单页表以这种为主。
  - **静态页面**：用去掉脚本的 `p1.html`，只适合原生控件，作为备用。

  可行性验证时两种都试，以验证结果为准（6.1）。
- 页面发往本机以外的请求一律拦掉。
- **提交的判定**：这一条用来测"永远不提交"。
  - 重放时，页面发出的所有非 GET 请求都转到本机的记录点，不转发到任何地方。
  - 录制时出现过的非 GET 请求（例如上传、保存草稿），按方法和去掉查询参数的地址列为"允许"。真实访问从不提交，所以录制时出现过的都不是提交。
  - 其余非 GET 请求一律判为"可能提交"，这次重测失败。
  - 填表 agent 点击过的按钮文字，命中配置里的提交按钮词表（Submit、Submit application 等）时，同样判为失败。
- 填表 agent 用同样的指令，只是地址换成本机地址。
- 重放不访问网站，可以反复运行，属于准备级。

### 6.5 每个岗位只真实访问一次

- 有录制的岗位，默认不再真实访问（规则见 4.1）。要再访问，在清单里写 `revisit: true`。处理完门槛、登录失败或补好标准答案后的重跑，由代码按上次的结论自动允许。
- 开发时的重测都用录制：改了读回、核对、评审或填表指令之后，在全部录制上重跑一遍，比较改前改后的报告。

## 7. 怎么测

### 7.1 离线单元测试（合成数据，fake client）

测试数据放在 `tests/fixtures/form_fill/`，明确标注为 synthetic。网页是手写的合成页面，不复制真实网站。要测的内容：

- **三个输入文件的 schema**：有一条不对，整份不运行；`contact.*` 写了值不通过；未知类别不通过；缺 `name.first` 或 `name.last` 不通过。
- **比较**：
  - 月份的各种写法、`otherwise`；
  - `yes_no`：选项不以 yes 或 no 开头时只认 `accept`；
  - `number_min`："95k"、"$95,000 - $110,000"、区间选项；
  - `url`；
  - `record`：子栏的 `accept` 和 `otherwise`、学校的 `aliases`、城市（多写了国家算格式，写成中文算错）、只有年份的起止；
  - 空着的栏：对上了答案的算缺漏，勾选框按答案判断，占位值算空；
  - 电话只比数字（带国家码、带括号），邮箱不分大小写。

  联系方式用一份假的 `profile.json` 测。
- **对题**：
  - 取最具体的短语："now or in the future" 对到 `sponsorship_future`。
  - 两条匹配到一样长的短语时，记为有歧义。
  - `asks` 优先于代码自带的写法。
  - agent 声明的键和代码对上的不同时，记为有歧义。
  - 重复段落按学校名（含 aliases）对到正确的一段；值里包含别名的也对得上（"百度（Baidu）"）；对不上的段记错的事实；
  - 短语按完整的词匹配；常见栏目要整句一样，Location、City 对到城市那条。
- **读回和编号**：
  - 控件：原生控件、仿 Workday 和仿 react-select 的结构、单选和复选题组、iframe；密码栏不读值。
  - 在页面中间插入一个追问栏后，原有栏的编号不变。
  - 两段 Education 的 School 栏编号不同。
  - 3 页表单缺了第 2 页 filled 时的读回，就用第 2 页的自动补录，补录的值是第 2 页填完后的值，不是第 3 页的空表；两样都缺时，第 2 页的栏全部是"读不出"。
- **页面预填**：
  - blank 时带值、filled 时值没变的栏，来源判定为页面预填，而且 `form/` 里没有这个值。
  - 某页没有 blank 录制时，没声明来源的非空栏记为"来源未录到"，不是"自己推断"，结论不是"可以提交"。
- **来源核验**：简历原句、求职信、键不存在的情况。
- **筛选题**：
  - 填表指令里有要求清单的全部条目。
  - 没有标准答案和简历原句、按清单条目作答且评审判定符合的栏，严重程度不是"无依据的猜测"。
- **上传核对**：上传的路径不是这个岗位上传目录里的文件，或者页面显示的文件不是本模块上传的，都记为错的事实。
- **严重程度和结论**：
  - 一条错的事实或一条无依据的猜测，就是"不能提交"。
  - 有读不出的栏，结论不能是"可以提交"。
  - "可能已提交"优先于其他结论。
  - 评审建议不影响结论。
- **缺标准答案**：多页合成表的第 2 页有一道必填题没有答案时，状态是 `needs_answer`，不是 `stuck`。
- **代码判定的状态**：用 fake CDP 测——同一页连续 3 次 filled 没有进展时返回 stop；标签页消失或 CDP 断开时记为 `tab_lost`。
- **修正单**：
  - 只收有确定值的；领英档案类的问题不收。
  - 修正 agent 最多 2 次，评审最多 3 次。
  - 同一个值连续两轮没改成，第 2 轮修正单里没有它。
  - 改了修正单以外的栏能被查出来；改前值有记录。
- **评审输出的校验**：栏目编号不存在、清单 id 不存在、简历原句不存在时，先重试一次，再不合格就记为评审失败。
- **评审材料**：没核验过的来源显示为"没有声明来源"；材料里没有填表 agent 的备注和自述。
- **命令构造**：用 fake 配置检查两条命令。
  - 填表 agent：`--disallowedTools` 含 `browser_run_code_unsafe`；MCP 服务表里有 checkpoint，没有 Gmail。
  - 评审：带 `--tools ""`、`--strict-mcp-config` 和空的 MCP 配置。
  - /apply 的命令和改动前一样。
- **隐私**：
  - 假 `profile.json` 里的每一项联系方式，都不出现在评审材料、报告、录制文件和运行记录里，只出现在填表指令里。运行记录里的密码写成"已填"。
  - 假页面上有一个不在假 `profile.json` 里的邮箱选项，它也不出现在这些地方。
  - 简历打码：邮箱、电话、住址都被替换。
- **网络记录**：cookie 和认证头被去掉；含联系方式的请求被丢掉；非 GET 请求不存内容。
- **录制编号**：已知平台和其他网站各一例；上次的结论决定重跑要不要 `revisit`。
- **重放服务**：外部请求被拦下；录制时没见过的非 GET 请求判为可能提交；点了提交按钮词表里的按钮也判为失败。
- 本模块不导入数据库模块（`store`）。

### 7.2 真实岗位（不进 CI）

- 用户挑一些真实岗位，每个真实填一次，得到录制。Greenhouse、Lever、Ashby、Workday、领英快速申请各至少覆盖一个。
- 用户照常亲手检查标签页，把发现的问题告诉 agent。每个问题对照报告，标成"报告查到了"或"报告漏了"。
- 漏掉的问题，原因在读回、对题、标准答案或要求清单中的某一处。按"用具体 case 迭代"来修：
  - 标准答案和要求清单怎么改，由用户选。
  - 改代码之前，先写一个能复现问题的合成测试。不为某个网站写特殊逻辑。
- 有了录制以后，重测只用录制。录制在 `data/local/` 里，所以相关测试只在本机运行，没有录制时跳过。
- 看三个数：
  - 每份录制里读得出的栏占多少；
  - 修正后还剩几个错的事实（目标是 0）；
  - 用户发现、报告却漏掉的问题有几个。

## 8. 第一版范围

已定（决定 25）。按切片分步做（决定 26，见本规格开头）。

**第一版做**：读清单 → 填表 → 停在提交前 → 读回 → 对照标准答案核对 → 独立评审 → 当场修正（最多 2 轮）→ 报告和录制。每个问题带一个评审猜测的原因类别。

**第一版不做**：

- 提交。任何岗位都停在提交前。
- 处理门槛和登录失败。验证码、单点登录、邮件验证码、重设密码都交给用户。
- 选岗位、选简历、写求职信。
- 写数据库或投递状态。
- 跨岗位的根因分析流程。等录了 20–30 个真实岗位再做，第一版只在汇总里列出反复出现的问题。
- 改领英档案或其他网站上的资料。
- 判断地点资格。
- 自动把评审的建议加进要求清单。

## 9. 和其他模块的接口

- **对外入口**（名称暂定）：
  - `check_form_fill_list(path)`，读级：校验清单和各输入文件，返回本次运行的摘要。
  - `start_form_fill(path, summary)`，提交级：真实访问网站，摘要必须和展示给用户的一致。
    - 加进 `.claude/settings.json` 的"每次询问"。
    - 在 `.codex/config.toml` 里设 `approval_mode = "prompt"`。
    - 带上 `anthropic/requiresUserInteraction` 标记（spec §10 第 8 条）。
  - `replay_form_fill(recordings)`，准备级：只在录制上重放。
  - `form_fill_status()`，准备级：查看进度和结果。
  - `get_form_fill_report(run, id)`，读级：返回报告，联系方式打码。
  - `get_redacted_resume(resume_id)`，读级：返回按 5.6 打码后的简历文本，起草标准答案时用（2.3）。`get_resume` 不变，仍返回原文。
- 对话里的入口是项目 skill `/form-fill`（在 Codex 里是 `$form-fill`），它只编排上面这些工具。
- **不依赖数据库**：输入都是文件；输出是标签页、文件和工具返回值。不读也不写岗位、意图、label 和投递状态。
- **和 /apply 共用的部分**：投递用的 Chrome（复制资料、删掉密码和自动填充、CDP 端口）、MCP 的固定版本、打不开的网站名单、受限读文件。这些都从 `apply_bridge.py` 复用，不改 vendor。
  - `apply_bridge.mcp_config` 和 `claude_command` 现在固定加载 Gmail 服务，放行名单读的是 `apply.allowed_tools`。
  - 本模块要给它们加参数，传入：
    - 自己的 MCP 服务表：Playwright 加 checkpoint，不要 Gmail（5.6）；
    - 放行名单；
    - 禁止名单。
  - /apply 的行为不变。
- **以后 /apply 怎么调用**：
  1. `prepare_apply_batch` 选出一批岗位；
  2. 写成清单：岗位编号作 id，加上申请地址、公司、职位、所选简历的 id、求职信路径；
  3. 调用本模块；
  4. 拿回每个岗位的 `{id, 结论, 需要你做的事, 报告, 录制编号}`；
  5. 写成什么投递状态由 /apply 自己决定，怎么映射在接入时再定。
- **配置**：`configs/default.yaml` 新增 `form_fill` 一节，包括：
  - 修正轮数（2）；
  - 填表模型和 `reviewer_model`；
  - 单个岗位的超时、`fix_timeout_seconds`；
  - `checkpoint` 的时限、判定卡住的次数（3）、后台补录读页的间隔（1 秒）；
  - `allowed_tools`、`disallowed_tools`；
  - 提交按钮词表；
  - 重放端口；
  - 数据目录下的各个路径。
- **代码位置**（建议）：`src/intent_job_agent/form_fill/`。按项目约定分成几个模块：
  - 输入和报告的 schema；
  - 纯逻辑：对题、比较、严重程度、修正单、打码；
  - 读回和录制（CDP）；
  - 重放服务；
  - 模型适配：评审的 Claude Code 后端（4.5）；
  - 运行器。
