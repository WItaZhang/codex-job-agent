## 2026-10-15 决定 1（用户）：模块边界

- 决定：
  - 填表是一个独立模块。
  - 输入是一个岗位清单文件（每条写申请地址、公司、职位、用哪份简历、用哪封求职信），加上投递资料。
  - 输出是每个岗位一个停在提交前的标签页，以及一份逐栏的填写报告。
  - 模块不读数据库，不碰意图，不挑岗位，永远不提交。
  - 以后 /apply 只负责把一批岗位转成清单，然后调用这个模块。
- 原因（起草时整理，用户未逐条确认）：原来的 /apply 把选岗位、写求职信、填表、提交和记状态放在一起，填错了也没办法单独测试填表。先把填表拆出来，边界清楚了才能验证。

## 2026-10-15 决定 2（用户）：什么算填对

- 决定：
  - 分两层核对：
    - 事实：姓名、联系方式、日期、学历、工作许可、EEO 等。由代码对照"标准答案"核对。
    - 判断项：要不要填选填栏、开放题的质量、格式。由一个新的评审 agent 按用户的"要求清单"检查，这个评审拿不到填表 agent 的任何上下文。
  - 评审自己发现的问题只算建议，用户同意后才进要求清单。
  - 多个岗位反复出现的问题，做根因分析，由用户选怎么改。
  - 报告里每一栏都写来源：标准答案的条目、简历原句、求职信，或者 agent 自己的推断。
  - 填入值由代码从页面读回，不用填表 agent 的自述。
  - 严重程度从重到轻：错的事实 > 无依据的猜测 > 缺漏（如选填的教育经历空着）> 格式。只要有一条错的事实，这个岗位就不能提交。
- 原因（起草时整理，用户未逐条确认）：
  - NOTE 是填表 agent 的自述，只有它自己注意到的才会写进去。已对照数据库核对：问题 1、2、4 都没在 NOTE 里出现；问题 3 在 NOTE 里只有一句笼统的提示，没写是哪几处；问题 5 是 agent 知道自己在猜，才写进了 NOTE。没有逐栏记录，用户只能逐个打开标签页检查。
  - 事实可以用代码比对，判断不能。
  - 评审看不到填表的过程，才不会被填表 agent 的解释带偏。
  - 一条错的事实就可能让这份申请作废，或者成为虚假陈述。

## 2026-10-15 决定 5（用户）：用真实岗位测试，并录成本地仿真表单

- 用户原话："我们用真实岗位，但是用一次就把它存到本地仿真表单，这样就可以解决重复和网站访问太频繁"。
- 决定：
  - 只用真实岗位测试。第一次真实访问时，把表单录下来，存成本地仿真表单，以后不访问网站也能重跑。
  - 每份录制保存每页的结构、截图和读回值。
  - 能如实重放的表单（多为单页的 Greenhouse、Lever、Ashby）可以重测填写。多步、靠脚本和接口驱动的表单（Workday、领英快速申请）大概只能重测核对和评审。每份录制都标明能重测什么。

  - 录制放在 git 忽略的 `data/local/` 下，空表和填入值分开存。
  - 确定性代码（对照标准答案、解析读回值、生成报告）照常用合成数据和 fake client 写离线单元测试。
- 原因：
  - 用户原话：同一个岗位反复真实填写，会重复，也会太频繁地访问网站。
  - 以下几条是起草时整理的，用户未逐条确认：
    - 合成表单重现不了 Workday、领英的多步表单。
    - Playwright MCP 不能逐页录制。
    - 先验证可行性，是因为还不知道两件事：第二个 CDP 客户端会不会干扰 Playwright MCP；自定义控件能不能读回。

- **换页补录**：`checkpoint` 服务在后台每隔 1 秒（配置）读一次岗位的标签页，只读不改。换页时，上一页最后一次读到的值就是这一页的补录。

  - 代价：离开前最后不到 1 秒里填的值可能没录到。`checkpoint("filled")` 仍是主要的读回，补录只在它缺了时用。
- **`checkpoint` 服务的形态**：本模块自己的 stdio MCP 服务，和 Playwright MCP 一起由填表 agent 的 Claude Code 启动，随填表 agent 退出。它用 Playwright `connect_over_cdp` 连投递用的 Chrome，整个运行保持一个连接，后台读页和 `checkpoint` 共用。它读 `profile.json` 只为打码。
- **认标签页**：`checkpoint` 带上填表 agent 当前页的地址（Playwright 回复里的 Page URL）。代码在这次运行开始后新开的标签页里按地址找，找不到再用上一次 `checkpoint` 的那个。每次都记下两边的地址，6.1 第 2 项据此判定。
- **页的标识**：标题取当前步骤（`aria-current="step"`）的文字，没有时取对话框或整页里全部标题的文字。标题一样、栏目却完全不同（两边各 2 栏以上、没有一栏相同）时，也算换页。
- **栏的身份**：页、所在题组（这一栏前面最近的标题）、题目原文、同一题组里同一题目第几次出现。后来出现的栏，`appeared_after` 记它前面最近的、已经编过号的栏：代码看不出是哪一栏触发的，取最近的。
- **来源**：2a 只由代码判"页面预填"和"来源未录到"。填表 agent 的来源声明在 2c 才有，在那之前其余非空栏写"未声明"，不按"自己推断"定严重程度（暂时的简化，只写在计划里）。
- **网络记录**：只记第一页加载时的 GET 响应。运行结束后，只有一页、没出现过密码栏、也没有一条响应带着联系方式（说明是登录后的页面）的录制，才留下 `network.json`，其余删掉。只有单页表能重测填写；规格原来写的"需要登录的页面不存网络记录"，由后两条交给代码判定。
- **MHTML**：按 MIME 拆开，逐段解码、打码后写回。写回后的文件打码扫描仍有命中，就不存。
- **`p<n>.filled.html`** 存填完时的简化页面，读回值以 `p<n>.values.json` 为准。没选"把读回值写进页面"：那要改页面的 DOM，或者另做一份克隆，克隆会运行页面自定义元素的代码。
- **报告**：运行结束时由代码直接出报告（每个岗位的 JSON 和 `summary.md`），本机命令 `report` 照旧可以重出。录制的 `meta.json` 记下最近一次的结论，供 4.1 判断要不要再真实访问。
- **6.1 第 8 项**（填完不调用 `checkpoint("filled")` 就翻页）：清单的岗位条目可以写 `ignore_filled_on_page: <页号>`，`checkpoint` 服务忽略这一页的 filled 调用（照常返回），看补录能不能接上。只用于可行性验证。
- **Workday 读回**：用主目录已存的两份 Workday 页面（打码后的简化 HTML 和读回）复现，改写成合成页面做测试，不为 Workday 写特殊逻辑。用这两份页面之前先问用户（CLAUDE.md）。
- `{{personal.email}}` 这种引用写法（5.6）是给重放用的，放到 2b；2a 的录制仍用类别占位（决定 14）。
- 原因：见每条后面。共同的考虑是切片要小、能单独合并，真实访问越少越好。

## 2026-10-21 决定 35（用户授权按推荐项）：一步卡住不结束对本模块的改动

- 起因：总规格决定 24（`spec.decisions.md`）。10-20 /apply 第一次在场试跑时，一个由本模块填的岗位，填表 agent 已经退出，这一步却一直是"运行中"：读回用的 Playwright 没有时限，页面不回应时会一直等。本模块冻结中，只做挡住 B 达标的这几处。
- 决定（用户 2026-10-21 授权自己跑，按推荐项）：
  - **读回有时限**（4.3）：读回和读一眼各在自己的线程里，最多 `apply.watchdog.read_seconds`（120 秒）；到时限结束这次读页的 Playwright 驱动，算读回失败（`readback_failed`），照总规格 §10 第 89 条记。
  - **agent 太久没有输出算卡住**（4.2）：结果码 `stalled`，报告照"卡住"写（和超时一样归到 `stuck` 这个原因），和填表 agent 自己报的 `stuck` 分开记在投递清单和尝试记录里。
  - **新的没填完原因"你停下了"**（3.2，`stopped`）：/apply 里说"停下"时，代码结束填表 agent，报告写明这个岗位没做完、没有提交。
- 没做：读回加上对话框处理器（没有处理器时 Playwright 会替页面关掉连上以后弹出的对话框，`checkpoint` 服务注册了空的处理器，读回没有）。离冻结的 2b、2c 近，列给以后。
